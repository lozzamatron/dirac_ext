## Verdict
SHIP WITH FIXES — the per-controller routing and registry lifecycle are sound, but the `FocusChatInput` rewrite drops the `show()` call for an already-visible webview (a real single-user regression), and one explicitly required audit guard (BannerService) was missed.

## Findings

1. **[medium] `src/extension.ts` (`commands.FocusChatInput`)** — The old handler *unconditionally* called `webviewView.show(preserveEditorFocus ? false : true)` on the resolved instance. The new handler only calls `show()` inside the `if (!instance)` branch. Concrete sequence: webview is visible but the user's focus is in the editor; user invokes "Focus chat input" (command palette / keybinding → `preserveEditorFocus = false`). Old behaviour: `show(true)` gave the webview OS focus. New behaviour: a visible instance short-circuits the branch, `show()` is never called, and the in-page `ShowWebviewEvent` cannot give the webview container OS focus — the command silently fails to focus. Smallest fix: after resolving `instance`, still call `(instance as VscodeDiracWebviewProvider).getWebview()?.show(!preserveEditorFocus)` (or at minimum when `!preserveEditorFocus`).

2. **[medium] `src/core/controller/index.ts` (constructor)** — The audit (§5 item 2) required guarding **both** `BannerService.initialize(this)` and `cleanupLegacyCheckpoints()` against N-controller re-runs; the diff only guards the latter via `legacyCheckpointCleanupStarted`. `BannerService.initialize(this)` still runs on every `Controller` construction. Latent while WP1 creates only the sidebar controller, but the moment a second Controller exists (WP2 tabs) BannerService is re-initialized per instance — exactly the hazard the audit flagged. Smallest fix: a module-level `bannerServiceInitialized` flag mirroring the checkpoint one (or make `BannerService.initialize` idempotent if its internals allow — unverified).

3. **[medium] `src/core/webview/InstanceRegistry.ts` (`controllerIdForTask`)** — When no registered instance has `controller.task?.taskId === taskId`, the function falls back to `lastActiveInstance()`, which can be a **different** controller. Concrete sequence (latent until tabs exist, but this is the exact cross-talk class WP1 exists to prevent): instance A is restoring a checkpoint; during the restore window `controller.task` is unset or mid-swap (e.g. during `clearTask`/`initTask` handoff); the user had recently interacted with instance B, so `lastActive` is B; `sendRelinquishControlEvent` from `CheckpointRestoreHandler`/`CheckpointDiffPresenter` then re-enables B's UI while A's UI stays permanently disabled — the worst-case outcome named in the brief. The comment says goal child tasks intentionally resolve via the fallback, so the smallest fix is not to remove the fallback but to make the failure loud: log a warning when the fallback (rather than an exact task match) is used for a relinquish-control event, so mis-routing is diagnosable. Flagging explicitly as latent-for-WP1, real-for-WP2.

4. **[low] `src/core/webview/InstanceRegistry.ts` (`disposeAll`)** — If any `instance.dispose()` rejects mid-loop, the remaining instances are never disposed and `this.instances`/`lastActive` are never cleared, leaving the registry pointing at disposed controllers for the rest of the process lifetime (subsequent `lastActiveInstance()` can return a disposed instance, since the ladder's third rung only checks `instances.has(recorded)`, not liveness). Smallest fix: wrap each `dispose()` in try/catch (or try/finally around the loop) so cleanup always completes.

5. **[low] `src/extension.ts` (PlusButton, SettingsButton, HistoryButton, WorktreesButton, FocusChatInput) / `src/hosts/vscode/review/VscodeCommentReplyHandler.ts`** — Several paths that previously **threw** (`getInstance()` threw when uninitialized) now warn-and-return silently. Only reachable in the no-instance state, and the warn logs make it diagnosable, but it is a throw→silent-return behaviour change for the single-instance user in the pre-init window. No fix required beyond awareness; noting per review criterion 3.

6. **[low] `src/core/controller/state/subscribeToState.ts` (`sendStateUpdate`)** — The `if (!responseStream) return` early-exit now happens *before* `recordStateSizeTelemetry(sizeBytes)`, so state-size telemetry is no longer recorded for publications with no subscriber (previously recorded unconditionally). Trivial; move the telemetry above the early return if the metric matters.

## Unverifiable from the diff (stated explicitly, not padded)
- Callers of `sendRelinquishControlEvent` and `sendAccountButtonClickedEvent` in unattached task code: `tsc` passing proves signatures were updated, but **not** that those callers pass the *correct* controller id (vs. e.g. a convenient-but-wrong id). The two checkpoint files in the diff are correct; the rest of the firing sites cannot be audited here.
- Whether the webview gRPC client's `request_id` namespace can collide across instances (audit §4 flagged this as UNVERIFIED) — no webview-client change appears in the diff; harmless while only one instance exists.
- `initializeTestMode(webview)` single-instance binding (audit §3 flag) — untouched, unverified, plausibly out of WP1 scope.

## Checked and found correct
- All nine per-webview registries converted to `Map<controllerId, handler>`; every `send…` no-ops on a missing id rather than broadcasting; OpenRouter/LiteLLM/checkpoint streams left as broadcasts per spec.
- Every cleanup closure in every converted subscription file is guarded by `get(id) === responseStream`, so a stale stream's cleanup cannot unsubscribe a newer subscription for the same controller id (the reload race).
- `subscribeToState` registers the map entry before awaiting initial delivery, and the error-path delete uses the same guarded check.
- `disposeAll` iterates a snapshot, so mutation-during-iteration is safe; `unregister` clears `lastActive` when it points at the disposed instance.
- `Controller.id` (ulid) is assigned before `webviewInstances.register(this)` in the provider constructor, and `getInjectedConfig()` is only invoked from `getHtmlContent()` post-construction — injection timing is safe; the config is now never empty, so the `__DIRAC_CONFIG__` script is always emitted (audit's caveat addressed).
- `StatePublicationQueue` callback passes `this.id`; `createTask`, `resetState`, `showTaskWithId` (all three sites), and `exports/index.ts` all pass the correct controller id.
- `PlusButton` → sidebar; Settings/History/Worktrees and accept/reject-edit → `lastActive ?? sidebar`; TerminalOutput → the instance `showWebview()` revealed (which is reliable because `FocusChatInput` calls `markActive()` before returning); `/task` URI → sidebar with last-active fallback; auth callbacks → last-active; `getWebviewHtml` → sidebar with a throw; `SharedUriHandler` visibility gate replaced with an existence gate; `TestServer` fallback added — all match the audit's routing table.
- `VscodeWebviewProvider` visibility handler marks active and targets `this.controller.id`; `getInjectedConfig` injects both `instanceId` and `surface`; `onDidChangeConfiguration` re-render re-injects the same stable id.
- For the single-sidebar user, `lastActiveInstance()` resolves correctly in every state (active+visible, visible-but-never-marked, hidden-but-registered) via the ladder's `visible()` and `sidebar()` rungs.
